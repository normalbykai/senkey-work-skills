# 本地 Git 提交

## 检查改动

1. 确认仓库与用户要求的范围，查看 `git status --short`、`git diff --stat` 和 `git diff --cached --stat`。
2. 通读范围内已暂存与未暂存的 diff；未跟踪文件需单独检查内容，不能只凭统计、文件名或单个文件概括。没有相关改动时说明并停止。
3. 按实际行为归纳变更组，选择 `feat`、`fix`、`refactor`、`chore` 等类型。互不相关的改动分别概述，不擅自混入同一次提交。

## 提交信息

- 主题格式：`类型(范围)：中文简明总结`。类型、范围及必要技术名词可用英文，主题总结与正文使用中文；用户明确要求其他格式或语言时遵循用户要求。
- 默认同时给出主题和“变更概述”，仅当用户明确只要主题时省略正文。
- 概述用 1–7 条覆盖所有有意义的变更组，按业务或技术目的合并，不为凑数拆分。每条写明影响范围、具体调整方式及行为变化；限制被放宽、收紧或删除时，说明新规则。
- 不使用“更新代码”“优化逻辑”等空泛描述，不把未验证的效果或未执行的测试写成事实。

```text
fix(报名)：修复重复提交产生多条报名记录的问题

变更概述：
- 报名接口：增加重复报名校验，已有有效记录时返回现有结果，避免重复创建。
```

示例仅展示格式，内容必须根据实际 diff 重写。

## 创建本地提交

1. 用户只要求分析或拟定信息时，到交付提交信息为止。用户明确要求提交时直接继续，无须重复确认。
2. 提交前确认暂存区只包含本次授权范围。使用明确路径暂存；同一文件夹杂无关修改时按块处理或澄清范围，不使用 `git add .` 或 `git add -A` 扫入全部改动。
3. 保留用户已有暂存状态；发现无关的已暂存内容时，不擅自取消暂存或一并提交。先明确本次提交范围，再采用保留无关暂存内容的方式提交。
4. 核对最终提交内容与信息一致。将主题、空行和“变更概述”写入 UTF-8 临时文件，通过 `git commit -F <文件>` 提交，避免多行内容的 shell 转义问题；临时文件放在仓库外。
5. 成功后读取最终提交信息及短哈希，回复实际提交的主题、完整概述和哈希；失败时如实说明，不声称成功、不跳过 hooks，检查失败后是否产生额外修改再决定后续操作。

## 边界

- 不提交无关文件、疑似凭据或未经用户要求的生成产物；发现疑似凭据时停止将其纳入提交，并说明位置，不展示秘密值。
- 不执行 push、amend、rebase、reset 或其他改写历史的操作，除非用户明确要求；本地提交授权不包含这些操作。
- 不为完成提交擅自修改业务代码，不丢弃用户修改。范围不明时继续只读分析，仅就影响提交的歧义提问。
